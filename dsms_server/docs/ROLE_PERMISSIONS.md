## 1. 角色定义

| 角色标识 | 角色名称 | 描述 | 适用场景 |
|----------|----------|------|----------|
| `no_permission_user` | 无权限用户 | 刚注册或离职的用户，无任何系统权限 | 新注册用户、离职用户 |
| `normal_employee` | 普通员工 | 可接收和发送消息，查看公告，查看部分系统信息 | 普通员工 |
| `device_admin` | 设备管理员 | 负责设备的添加、审批、状态监控等管理操作 | 设备运维部门 |
| `detection_monitor` | 质检监控员 | 负责监控检测记录、缺陷详情、人工审查等检测相关操作 | 质检部门 |
| `hr_admin` | 人事管理员 | 负责人事管理、部门管理、职称管理等人力资源操作 | 人力资源部门 |
| `senior_sys_admin` | 系统管理员 | 负责系统配置、角色权限管理、审计日志查看等系统管理操作 | IT运维部门 |
| `super_sys_admin` | 超级系统管理员 | 拥有系统最高权限，可进行所有操作 | 系统管理员 |

## 4. 权限管理说明

### 4.1 权限继承原则

1. **超级管理员**：拥有所有权限，不受权限配置限制
2. **权限累加**：用户权限为其角色权限的集合
3. **路径匹配**：支持通配符 `*`，如 `/api/v1/users/*` 匹配所有用户相关接口
4. **方法匹配**：支持通配符 `*`，表示所有 HTTP 方法

### 4.2 权限存储格式

权限以 JSON 格式存储在角色表的 `permissions` 字段中：

```json
[
  {"api": "/api/v1/users/*", "accessibility": "*"},
  {"api": "/api/v1/devices/*", "accessibility": "GET"},
  {"api": "/api/v1/admin/*", "accessibility": "*"}
]
```

### 4.3 权限检查流程

```
请求到达 → 认证中间件 → 权限检查中间件 → 路由处理
              ↓               ↓
          验证Token      检查API权限
              ↓               ↓
          获取用户信息    匹配权限规则
              ↓               ↓
          设置角色ID     判断是否允许访问
```

## 5. 权限格式规范

### 5.1 API路径格式

| 格式 | 说明 | 示例 |
|------|------|------|
| 精确匹配 | 完全匹配指定路径 | `/api/v1/users/me` |
| 通配匹配 | 匹配路径下所有子路径 | `/api/v1/users/*` |
| 全局匹配 | 匹配所有路径 | `*` |

### 5.2 访问权限格式

| 值 | 说明 |
|----|------|
| `GET` | 仅允许 GET 请求 |
| `POST` | 仅允许 POST 请求 |
| `PUT` | 仅允许 PUT 请求 |
| `DELETE` | 仅允许 DELETE 请求 |
| `*` | 允许所有请求方法 |

### 5.3 权限配置最佳实践

1. **最小权限原则**：只授予必要的权限
2. **使用通配符**：合理使用 `*` 减少配置量
3. **角色分级**：按照职责划分角色权限
4. **定期审计**：定期检查权限配置的合理性
